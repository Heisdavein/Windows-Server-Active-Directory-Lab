## Overview

As I progressed through my Windows Server project, I wanted to become familiar with one of the most important troubleshooting tools available to every Windows administrator — **Event Viewer**.

Almost everything that happens on a Windows Server is recorded somewhere, and Event Viewer is where those records are stored.

Whether a user signs in, a service starts successfully, a driver fails, a piece of hardware encounters an error, or a security event occurs, Windows logs the activity for future reference.

I quickly realised that knowing how to navigate Event Viewer is an essential skill for an IT Support Engineer or System Administrator.

Rather than guessing why something is not working, Event Viewer often provides the evidence needed to identify the root cause of a problem.

---

## Opening Event Viewer

To access Event Viewer, I:

1. Right-clicked the **Start** menu.
2. Selected **Event Viewer**.

Alternatively, I could open the Start menu, search for **Event Viewer**, and launch it from the search results.

Once the console opened, I could begin exploring the different categories of logs that Windows maintains.

> **Why this matters:**  
> Event Viewer gives administrators a central place to investigate activity and errors recorded by Windows and installed applications.

---

## Understanding Windows Log Categories

In the left-hand navigation pane, I expanded **Windows Logs**.

I found several different log categories, with each one recording a different type of activity within the operating system.

### Application

The **Application** log contains events generated by software installed on the server.

This includes:

- Microsoft applications
- Third-party software
- Databases
- Custom business applications

If an application crashes or encounters an unexpected error, this is usually one of the first places I would investigate.

---

### Security

The **Security** log records authentication and auditing events.

Examples include:

- Successful and failed sign-in attempts
- Account lockouts
- User account creation and deletion
- Changes to security groups
- Permission changes
- Group Policy events

I found this log particularly important because it plays a major role in security monitoring, auditing, and incident investigations.

---

### Setup

The **Setup** log records events related to:

- Windows installation
- Server roles
- Windows updates
- Component installations

This log can be especially useful when troubleshooting installation failures or deployment issues.

---

### System

The **System** log contains events generated by Windows itself.

Typical events include:

- Driver failures
- Hardware issues
- Service startup failures
- System shutdown events
- Operating system errors

Whenever I need to investigate why Windows is not behaving as expected, the **System** log is usually one of the first places I check.

---

### Forwarded Events

The **Forwarded Events** log stores events that have been collected from other Windows computers and forwarded to this server.

I did not configure event forwarding in my lab, but I learned that this feature is commonly used in enterprise environments to centralise log collection from multiple servers.

> **Note:**  
> Although I did not configure event forwarding in this project, understanding what the log is used for helped me see how Event Viewer can scale beyond a single server.

---

## Understanding Event Levels

Every event recorded in Event Viewer is assigned a severity level.

These levels make it easier to identify which entries deserve immediate attention.

### Information

**Information** events are normal operational messages.

They indicate that Windows or an application has completed an expected action successfully.

Most events recorded on a healthy server fall into this category.

---

### Warning

**Warning** events indicate that something unusual has occurred.

The issue may not have caused an immediate failure, but it could become a problem if left unresolved.

---

### Error

**Error** events indicate that something has gone wrong.

Examples include:

- Failed services
- Application crashes
- Hardware problems
- Driver failures

These are often the events I would investigate first when troubleshooting a problem.

---

### Critical

**Critical** events represent the most serious issues.

They usually indicate that the operating system or a major component experienced a severe failure that affected the stability or availability of the server.

> **Troubleshooting approach:**  
> When investigating a problem, I can start with Critical and Error events before working through less severe entries.

---

## Reading an Event

To better understand how Event Viewer works, I selected several events and reviewed the information displayed in the details pane.

The fields I found most useful were:

### Event ID

The **Event ID** is a unique numerical identifier assigned to each type of event.

I discovered that searching for an Event ID online often leads directly to Microsoft documentation or community discussions explaining the event and possible solutions.

### Source

The **Source** identifies the application, service, or Windows component that generated the event.

### Description

The **Description** provides a detailed explanation of what occurred.

It often contains enough information to begin troubleshooting.

Learning to interpret these three fields made Event Viewer much less intimidating and significantly easier to navigate.

## Filtering Event Logs

One thing I noticed immediately was how quickly Event Viewer fills with information.

Even a freshly installed server can generate hundreds or thousands of events within a short period.

Rather than scrolling through everything manually, I learned how to filter the logs to display only the events relevant to my investigation.

### Filtering by Event Level

I used the following process:

1. I right-clicked a log, such as **System**.
2. I selected **Filter Current Log**.
3. Under **Event Level**, I selected:
   - **Critical**
   - **Error**
4. If I wanted to investigate a specific event, I could also filter by **Event ID**.
5. For example, entering `4624` or `4625` in the Security log would display only those events.
6. I clicked **OK**.

Event Viewer then displayed only the matching log entries.

This made troubleshooting much faster because I did not have to manually search through every event.

> **Example:**  
> If I was investigating suspicious sign-in activity, I could filter the Security log for Event ID `4624` or `4625` rather than reviewing the entire Security log.

## Security Event IDs I Learned

While exploring the Security log, I came across several Event IDs that administrators frequently monitor during security investigations.

| Event ID | Description |
|---|---|
| `4624` | Successful user logon |
| `4625` | Failed logon attempt |
| `4740` | User account locked out |
| `4720` | User account created |
| `4726` | User account deleted |
| `4728` | User added to a security-enabled global group |

### Why These Event IDs Matter

These Event IDs gave me a practical introduction to how administrators investigate activity inside a Windows environment.

For example:

- `4624` can help identify successful authentication activity.
- `4625` can help identify failed authentication attempts and may be useful when investigating possible brute-force attacks.
- `4740` can show when an account has been locked out.
- `4720` can show when a user account was created.
- `4726` can show when a user account was deleted.
- `4728` can show when a user was added to a security-enabled global group.

These Event IDs are among the commonly referenced events during Windows security monitoring.

Becoming familiar with them gave me a better understanding of what administrators look for when reviewing security logs.

## Creating a Custom View

To make future troubleshooting easier, I created a custom view that automatically displays the most important events from every Windows log.

### Step 1 — Open Custom Views

In the Event Viewer navigation pane, I right-clicked **Custom Views**.

I selected:

**Create Custom View**

### Step 2 — Select Event Levels

I selected:

- **Critical**
- **Error**

This meant the custom view would focus on the most serious event levels.

### Step 3 — Select the Logs

Under **By Log**, I selected:

**All Windows Logs**

### Step 4 — Save the Custom View

I clicked **OK**.

When prompted for the name, I entered:

```text
All Errors and Criticals
```

The custom view was then available under **Custom Views**.

### Why I Created This View

Instead of manually opening each Windows log and filtering it every time, I can select **All Errors and Criticals** to quickly see critical errors across the server.

Creating this custom view made troubleshooting much more efficient.

It also showed me how Windows administrators can tailor Event Viewer to suit their own workflow.

---

## Verification

After creating the custom view, I verified that:

- The **Custom Views** section contained the new view.
- The view was named **All Errors and Criticals**.
- The view was configured to display **Critical** and **Error** events.
- The view covered **All Windows Logs**.
- Selecting the view displayed matching critical and error events from the server.

I also tested the standard filtering process by filtering logs for specific event levels and Event IDs.

This gave me practical experience with both targeted log filtering and reusable custom views.
